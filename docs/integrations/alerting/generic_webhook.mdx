---
title: "Generic Webhook"
description: "Create Incidents from authenticated alert events."
---

Use Generic Webhook when your alerting system can send JSON over HTTP. OpenCluster groups firing and resolved Alert Events into Incidents. Configure any field mappings in the sender.

## Connect

You need the OpenCluster **Admin** role and a sender that can reach the HTTPS webhook endpoint and set request headers. Use the [API session and Origin setup](/api-reference/overview#authentication):

```bash
curl --fail-with-body --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
  --data '{"type":"generic_webhook","name":"Database alerts","configuration":{}}' \
  "$OPENCLUSTER_URL/api/v1/integrations"
```

Save `integration.id`, `integration.webhook.url` and the one-time `webhookSecret`. Set `WEBHOOK_URL` to that URL and set `WEBHOOK_SECRET` privately. Send a firing event:

```bash
curl --fail-with-body --include \
  --header "X-OpenCluster-Token: $WEBHOOK_SECRET" \
  --header 'Content-Type: application/json' \
  --data '{
    "eventId": "database-0042",
    "status": "firing",
    "title": "Database latency is high",
    "severity": "critical",
    "startedAt": "2026-08-28T07:00:00Z",
    "deduplicationKey": "production/database-latency"
  }' "$WEBHOOK_URL"
```

Send the resolution with the same event ID, start time and deduplication key, set `status` to `resolved` and add `resolvedAt`. Optional fields include string maps for `labels` and `annotations`, and an HTTP(S) `sourceUrl`. See the [webhook contract](/api-reference/overview#webhooks) for the full schema.

## Verify and use

A new delivery returns `202 Accepted`. An exact retry returns `200 OK`. Call the [verification endpoint](/api-reference/overview#verify-an-integration) to see the last accepted delivery, then list Incidents with `GET /api/v1/incidents`.

A new firing Incident queues an Investigation when a model provider is configured. Alert fields supply Incident context. For runtime or change data, connect an additional Integration.

## Troubleshooting

- **400.** Check required fields, timestamps and event identity. Reusing an event ID with different content in the same phase is refused.
- **401.** Check the current secret and confirm the Integration is enabled. Rotation invalidates the old secret immediately.
- **413.** Reduce the request body below the 1 MiB limit.
- **503.** Retry with bounded backoff and honor `Retry-After` when supplied. Keep the same event identity.
