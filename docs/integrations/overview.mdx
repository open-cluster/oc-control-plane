Connect OpenCluster to the tools your team already uses. Metrics, logs, traces, infrastructure state, code changes, and team discussions help answer operational questions and investigate incidents. An alert is not required.

Start with a source that can answer your question. An integration may serve several purposes, such as Slack providing both an interaction channel and evidence.

## Observability

Connect [Prometheus](/integrations/observability/prometheus), [Loki](/integrations/observability/loki), and [Tempo](/integrations/observability/tempo) for metrics, logs, and distributed traces.

Ask “Why did checkout latency increase during the last 30 minutes?” OpenCluster can compare available measurements, log excerpts, and example traces, citing the evidence behind its findings.

## Infrastructure

Connect [Kubernetes](/integrations/infrastructure/kubernetes) to inspect a named workload and its pods, namespace events, and container logs. Relay runs in your environment and keeps Kubernetes credentials there.

## Source control

Connect [GitHub](/integrations/source-control/github) for commits, pull requests, CI failures, files, and releases in selected repositories. OpenCluster uses a GitHub App with read-only repository permissions.

## Collaboration

Connect [Slack](/integrations/collaboration/slack) to ask questions through direct app mentions and continue conversations in threads. Slack questions can use other connected sources. Their Slack evidence reads stay within the originating thread.

Slack can also provide permitted discussion history as evidence for questions started through the Conversation API. Access depends on the connected token, its scopes, and channel membership.

## Alerting

Connect [Prometheus Alertmanager](/integrations/alerting/alertmanager) or [Generic Webhook](/integrations/alerting/generic_webhook) to create and update incidents from incoming alerts. Alert sources are optional.

## Access and connection

An Admin creates an integration or authorizes its provider installation. GitHub and installed Slack apps use provider authorization. Slack also accepts existing tokens for read-only access. Kubernetes requires a Relay, and alert senders need a webhook URL and secret.

Each guide explains required access, connection methods, examples, and limitations. Administration currently uses the [API connection procedures](/api-reference/overview#connect-an-integration). A web setup experience is under development.

A successful connection check confirms access at that time. Source permissions, retention, and availability still affect later reads. Kubernetes needs an explicit Relay capability check during setup. Alert sources can receive alerts before verification, and waiting for a first delivery alone does not indicate an outage.

## Disconnect

An Admin disconnects an integration with `DELETE /api/v1/integrations/{integration}`. Disconnect removes its saved credentials and webhook secret, releases its provider installation, and prevents new reads and incoming processing. It disappears from the Installed list. Prior investigations, evidence, conversations, and source references remain available. Repeating Disconnect is safe.

Create a new integration with fresh credentials or provider authorization to connect again. Disconnect does not necessarily uninstall the GitHub or Slack app or revoke credentials at the provider. A provider request already admitted before Disconnect may finish afterward. Subsequent operations must check access again.
