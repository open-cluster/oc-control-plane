OpenCluster checks your identity and Organization role before granting access to data or operations.

Report vulnerabilities through the process in `SECURITY.md`. Do not open a public issue
containing sensitive details.

## Authentication and authorization

Initial local signup creates the first Organization and its Admin account. Follow the
private initialization instructions for [Docker Compose](/self-hosting/docker-compose)
or [Helm](/self-hosting/helm). Signup requires
the configured same Origin even before a cookie exists. The Origin check protects browser
requests, but does not establish deployment ownership.

API requests use the browser session cookie. Unsafe requests require the configured
same-origin `Origin`. Cross-origin and `Origin: null` requests are rejected.

Browser sessions expire after 12 hours without renewal or seven days after sign-in, whichever comes first.
Foreground activity can renew a session when your frontend supports [session refresh](/api-reference/sessions/refresh-the-current-session). Idle tabs and background requests do not renew it.

Roles grant fixed Permissions inside an Organization. Missing authentication returns
`401`, insufficient Permission returns `403`, and inaccessible Organizations and unknown
tenant records are indistinguishable.

A User has at most one current Organization Membership. Organization Admins can create
local Users and manage that Membership, but cannot replace an existing User's password. Change your own
local password with `PUT /api/v1/auth/local/password`, supplying `currentPassword` and
`newPassword` without an Organization selector. Success deletes all your sessions, including
the current one, and requires sign-in again. New passwords for bootstrap, local-user creation, password change and recovery accept 12–1024 UTF-8 bytes. The current password must be nonempty and at most 1024 bytes. OpenAPI string lengths count characters. Clients must measure UTF-8 bytes to match validation. Sign-in verifies the stored credential without reapplying creation-length rules.
OIDC Users manage their credentials through their identity provider.

Deployment operators can recover an existing enabled local account using its User UUID:

```sh
controlplane recover-local-password --user USER_UUID < /run/secrets/recovery-password
```

Run this with the deployment's existing configuration and database access. Supply the new
password only through redirected or piped stdin. Terminal input and password arguments are
refused. One trailing line ending is accepted. Recovery changes the password, deletes all
the User's sessions and records the action atomically. Unknown and OIDC-only accounts are
refused. Recovery does not create Users or reactivate bootstrap.

Tokenless signup is available whenever both Organization and User records are absent.
The first caller who reaches an empty deployment can create the Admin. Protect the entire
backend from untrusted network access until that Admin exists. An Origin header, Host
header, forwarded address, or localhost-looking request is not proof of ownership.

Compose publishes the API on host loopback. Use a patched Docker Engine 28.0.0 or newer with standard
bridge networking and no remote direct routing or public proxy forwarding during setup.
Trust local host processes and containers on that Docker network. Helm uses a ClusterIP
Service by default, which is **not** isolation from other Pods. Apply appropriate network
restrictions and perform first signup through a trusted connection, such as an authorized
loopback-bound port-forward, before enabling public ingress. An accidentally reset or
replaced database reopens signup and must also be initialized privately.

Retained Organizations and Users close signup across restarts, upgrades, Membership
removal, disabled accounts, and ordinary account removal. Concurrent signup is serialized
in PostgreSQL. Remove obsolete administrator token inputs and
`security.bootstrapTokenFile` from old YAML before upgrading. No signup-specific schema
migration is needed. Relay enrollment credentials remain separate and unchanged.

Sessions belong to the User and store no Organization or Role. Each request resolves the
User's one current Membership, so Role changes take effect immediately and Membership
removal prevents authentication without deleting identity history.

Logout deletes the current authorized session and clears the browser cookie. If a
membership has been removed, the now-unusable cookie can still be cleared and the
orphaned session expires through normal cleanup.
An absent or expired cookie can be cleared again. Logout still requires the configured
Origin. When session revocation fails, logout returns an error and leaves the valid cookie
intact so the user can retry.

## Trust boundaries

The browser and product ingress share one origin. PostgreSQL holds durable product truth.
Customer Relays initiate outbound, pinned sessions. The control plane never receives
cluster credentials. Integration and model providers remain external trust boundaries,
and their returned content is always untrusted input.

Changing an Organization identifier does not change the User's identity: the server
rejects a value that does not match the current Membership before a Tool is offered or a record is read. A Kubernetes read can
cross the Relay boundary only when the registered capability and namespace allow-list
both permit it.

Read-only Tools reduce change risk but do not make source data harmless or complete.

Prometheus, Loki and Tempo requests go directly from OpenCluster to the configured
endpoint. Use approved HTTPS destinations and restrict deployment egress. These
Integrations verify TLS certificates and reject redirects. The deployment does not
enforce a destination allowlist. Admins and Editors can change endpoint settings.
An edit that omits a credential retains it, so review the destination before
changing configuration. Enforce tenant access, query limits and retention at the source.

## Data handling

OpenCluster stores normalized Alert Events, Incidents, Messages, Investigation events,
Tool Runs, cited Findings, audit records, and draft Postmortems in PostgreSQL. Tool
Runs retain bounded observations prepared for the model, capped at 64 KiB each. Editors
and Admins can retrieve one observation on demand. Viewers retain summary and metadata
access. Ordinary detail requests and activity events omit observation bodies.
Conversations retain continuity through
Messages and prior cited Findings. OpenCluster does not persist or expose model
chain-of-thought.

An Investigation can perform live authorized reads, including bounded Kubernetes
container logs through Relay and Slack channel or thread messages. A configured Slack App
can also send originating-thread replies. These reads and replies remain constrained by
the Integration's verified permissions and the current Organization.

Retention and backup policy are deployment responsibilities in OSS. Protect backups as
production data and verify retention changes against legal and operational requirements.
Observations follow their Investigation's existing retention practices and have no
independent expiry. Known credential-shaped argument fields and opened credential
reflections are removed before new observation persistence. This does not detect every
secret: retained source excerpts can still contain sensitive operational data.

A retained observation is limited to 64 KiB, including its headers and arguments. Content prepared for the model has a separate 16 KiB budget. Retained observations may therefore contain more source content than the model received. Protect observation access and backups accordingly.

## Secrets and Relay

Secrets accept a direct environment value or an optional `_FILE` path, never both. Startup errors omit secret values and paths. Restart after changing configuration or secret files.
Inbound webhook credentials are stored as digests. Presentable Integration credentials
are sealed and never returned after creation. One-time values must be stored immediately.
Audit details remove credential-shaped keys.

The Relay initiates its connection from the customer boundary, validates configured SPKI
pins, and executes only closed protocol capabilities. Kubernetes credentials remain with
the Relay and never enter the control plane. Read-only capabilities still require
least-privilege Kubernetes RBAC, network controls, credential rotation, and encryption-key
custody.

Losing the encryption key leaves product records readable but makes sealed Integration
credentials unrecoverable. Back it up separately from PostgreSQL.

## Model-provider boundary

For an Investigation, OpenCluster may send the subject, question, bounded time window,
connected Tool catalog, normalized alert context, bounded prior cited Findings, and
summarized Tool results to the configured model provider. It does not send Tool
credentials or publish model chain-of-thought.

The provider returns Tool requests or a structured conclusion. OpenCluster validates
budgets, citations, enums, and result bounds before persistence. Deployment owners must
review provider retention, training, regional processing, contractual terms, and the
source content allowed to cross this boundary.

Deployment owners remain responsible for HTTPS, identity-provider policy, provider terms,
retention, backups, and secret custody. Use [Configuration](/self-hosting/configuration)
to apply the shipped controls.

## Manage Integrations

Store one-time webhook secrets securely. When an Admin rotates a secret, update the sender promptly because the old secret stops working immediately. Only Admins can [disconnect Integrations](/integrations/overview#disconnect). Disconnect clears saved credentials and stops new use while preserving historical records.

## Using the API securely

Sign in through local authentication or OIDC and use the issued session cookie for subsequent API requests. Treat the cookie as a credential. Include an Origin header matching the deployment public URL on write requests, including when using generated request examples. The session determines your Organization and role.

For provider authorization, sign in and start Connect from the same browser session on the public HTTPS origin. Follow the returned authorization URL and keep that session open for the callback.
