---
title: "Secrets and Relay"
description: "Protect file-backed secrets and understand the Relay's outbound trust model."
---

Environment variables name secret files rather than containing credential values. Inbound webhook credentials are stored as digests. Presentable Integration credentials are sealed and are never returned after creation; one-time values must be stored immediately.

The Relay initiates its connection from the customer boundary, validates configured SPKI pins, and executes only closed protocol capabilities. Fencing prevents stale sessions from recording work twice. Kubernetes credentials remain with the Relay and never enter the control plane.

Back up the encryption key separately and rotate credentials using their dedicated operation.

For example, rotating a webhook secret immediately invalidates the former digest, while
rotating a presentable provider credential seals its replacement. A Relay with an
unrecognized SPKI pin or unsupported capability cannot perform the read.

Read-only capabilities do not remove the need for least-privilege Kubernetes RBAC,
network controls, credential rotation, and backup-key custody. Losing the sealing key
leaves product records readable but makes sealed Integration credentials unrecoverable.
