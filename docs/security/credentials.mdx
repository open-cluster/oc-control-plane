---
title: "Credential handling"
description: "How every secret OpenCluster touches is stored, what can be read back (nothing), and what rotation means for each."
---

The rule everything below follows: a credential is stored in the weakest form that
still works, is never readable back, and every use that can be audited is.

## Every credential, at rest

| Credential | At rest | Read-back |
| --- | --- | --- |
| Webhook secrets (Alertmanager) | SHA-256 digest only | Never — shown once at creation or rotation |
| Pasted integration tokens (Slack) | Encrypted, AES-256-GCM, under the deployment's sealing key | Never — reads show a random fingerprint, not anything derived from the token |
| Identity provider client secrets | Encrypted, same key | Never |
| Sessions and API tokens | Digests | Never |
| GitHub App key, model API key, database credentials | Files on the deployment, named by configuration — never environment values | Not stored by OpenCluster at all |

## The properties that matter

- **Verified before stored.** A pasted token is proved against its vendor first; a token
  the vendor refuses is never written anywhere.
- **Write-only after entry.** No API returns a stored credential. Fingerprints are
  minted at random, never derived, so a database dump cannot confirm a guessed token
  offline.
- **Bound to their place.** An encrypted credential is cryptographically bound to its
  own integration; copied onto another record, it refuses to open.
- **Every use is audited first.** Each time an investigation or verification opens a
  stored credential, the audit record is written before the credential is used — a use
  that cannot be recorded does not happen.
- **Constant-time comparison** for every inbound secret, checked before anything else
  about the request is considered.
- **Never in logs or errors.** Configuration names files rather than carrying values, no
  error quotes a secret file's contents, and secret values render as placeholders in
  every format a log can reach.

## Rotation

- **Webhook secrets** rotate from the integration page: a new secret is shown once and
  the old one stops working immediately, with no overlap window.
- **Pasted tokens** rotate by pasting the new token; it is verified live and replaces
  the old one in a single step.
- **The deployment's sealing key**: rotating it makes previously stored credentials
  unopenable. Each affected integration then verifies as failed with "paste it again to
  replace it" — re-paste the credential; nothing else is lost. Encrypted values carry a
  key version, so a deployment-managed re-wrap is possible without mass loss.
- **GitHub** needs no stored per-integration secret at all: the App's key stays with the
  deployment, and access tokens are minted short-lived per installation and held only in
  memory.

## What OpenCluster never holds

- Your cluster's credentials — the Relay inside your cluster holds its own service
  account, and OpenCluster can narrow but never widen it.
- Plaintext webhook secrets, session identifiers or API tokens — digests only.
- Any credential in an environment variable, a log line, an error message or an audit
  detail.
