Use an authenticated session and include the Origin header on write requests. See [Authentication](/api-reference/overview#authentication).

## Initial local signup in a browser

For a new installation, open `/setup` in a compatible frontend over the deployment owner's
trusted private connection. Follow [Compose](/self-hosting/docker-compose) or
[Helm](/self-hosting/helm) to restrict deployment access during initialization. A compatible frontend provides the setup page and calls the OpenCluster API.

The form shows **Create your OpenCluster account** and submits Organization name, email,
optional display name, and password to `POST /api/v1/auth/local/bootstrap` as JSON:

```json
{
  "organizationName": "Platform Team",
  "email": "admin@example.com",
  "displayName": "Admin",
  "password": "<user-chosen-strong-password>"
}
```

The browser-facing origin must equal `OC_PUBLIC_URL`. Route `/api/` through the frontend's
same-origin proxy to the backend. Preserve the browser's `Origin` and forward `Set-Cookie`
without rewriting its name, Domain, Path, Secure, or HttpOnly attributes. Use HTTPS, or a
browser-supported trustworthy localhost origin for local setup. Do not use a plain HTTP LAN
address or configure the backend URL as the browser origin when the frontend uses another port.

On **Create account**:

1. Send the signup JSON with `Content-Type: application/json` using same-origin fetch.
2. On `201 Created`, let the browser store `__Host-oc_session` automatically.
3. Fetch `GET /api/v1/session` with the same browser session, update authentication state,
   and navigate client-side to the dashboard. Retry session retrieval if it temporarily fails.

There is no second sign-in request, manual cookie handling, or full page reload.
Refresh server-rendered session-dependent content only if the frontend needs it.
Signup returns `403` when Origin is refused, and `409` when already initialized. A lost signup response may require normal sign-in with the account just submitted.

Normal visits call `GET /api/v1/session`: render the application on success and sign-in on
`401`. Show an availability error for a server failure. Do not automatically redirect to signup
or probe bootstrap to discover setup state. Other Users are created by an Admin through the
existing local-user API. Do not expose a fresh or reset database publicly before an Admin has been created.

## Investigation observations

Use `GET /api/v1/investigations/{investigation}/runs/{ordinal}/observation` to inspect
one cited Tool Run as an Editor or Admin. The response returns bounded prepared text and
source context. Older unavailable observations are `null`. Viewer access returns `403`.
Ordinary Investigation detail, lists, and events omit these bodies. See
[Observation response details](#observation-response-details)
for clipping, timing, sensitivity, and retention semantics.

## Integration catalog

Use `GET /api/v1/integration-types` for the supported-provider catalog. Each card contains only `key`, `name`, `description`, and `category`, ordered by key. The catalog has no query parameters, pagination, configured counts, or public Tool schemas.

Select a provider with `GET /api/v1/integration-types/{type}`. Detail adds `requiresRelay`, `supportsConnect`, and `configurationFields`. Each field contains `key`, `type`, `required`, `secret`, and applicable `options`. No secret values or deployment credentials are returned. Field order follows the provider's configuration. An unknown key returns 404.

`required` describes unconditional manual-creation requirements. Provider checks still enforce conditional rules, such as a Basic username and token. Supply `relayId` at the top level when required. `supportsConnect` means the deployment can start provider authorization, not that delivery or provider availability has been tested. GitHub requires provider authorization. Slack also supports existing read-only tokens.

Use `GET /api/v1/integrations` separately for the active connections owned by your Organization. Multiple instances can share a type. Instance lists retain pagination and search. Per-Integration `toolAvailability` reports verified grants and eligibility for registered operations. It is not a live health check. Setup guides explain provider access and authentication requirements.

## Verify an Integration

Set `INTEGRATION_ID` to the ID returned during setup. An Editor or Admin can request verification:

```bash
curl --fail-with-body --request POST --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" \
  "$OPENCLUSTER_URL/api/v1/integrations/$INTEGRATION_ID/verify"
```

Use the returned `status` and `toolAvailability` for technical diagnosis. `verificationNote` may be included in verification and credential mutation responses. Ordinary reads do not reconstruct it. Query-source creation and provider authorization already probe access. Kubernetes needs this explicit check. For webhook sources, this operation reports accepted delivery history and returns `failed` when none exists. That alone does not establish an outage.

Prometheus checks the expected result of `vector(1)`. Loki checks a one-minute log query limited to one entry. Tempo runs a bounded trace search. Valid empty Loki and Tempo results confirm query access. Tempo trace retrieval can still require separate permission.

## Authorize GitHub or Slack in a browser

**Advanced workaround for API-only deployments.** Use your browser's developer console
to start authorization with the same browser session that receives the provider callback.

Use the deployment's public HTTPS origin. Check `supportsConnect` in `GET /api/v1/integration-types/{type}`.

1. Open `/healthz` on the OpenCluster origin in your browser. For OIDC, first visit `/api/v1/auth/oidc/start` on that origin and complete sign-in. For local authentication, open the browser's developer console on the OpenCluster origin and run:

   ```js
   const signIn = await fetch("/api/v1/auth/local/sign-in", {
     method: "POST",
     headers: {"Content-Type": "application/json"},
     body: JSON.stringify({
       email: prompt("OpenCluster Admin email"),
       password: prompt("OpenCluster password"),
     }),
   });
   if (!signIn.ok) throw new Error("Sign-in failed: " + signIn.status);
   ```

2. In the same browser, start setup. Replace `github` with `slack` for Slack:

   ```js
   const setup = await fetch(
     "/api/v1/integration-types/github/connect?returnTo=%2Fapi%2Fv1%2Fsession",
     {method: "POST"},
   );
   if (!setup.ok) throw new Error("Setup failed: " + setup.status);
   location.assign((await setup.json()).authorizationUrl);
   ```

3. Approve the installation at the provider and return in the same browser. The redirect goes to the session endpoint. Check its URL for `connect=connected` and the `integration` ID. Open `/api/v1/integrations/<integration-id>` on the same origin to confirm its status. If setup fails or expires, start again.

A cURL cookie jar is separate from your browser session. The callback needs the browser session that started setup.

For an App you already installed in GitHub, use the existing-installation option in the [Connect operation](/api-reference/integration-types/start-provider-authorization).

## Connect an Integration

An Admin creates Integrations or starts provider authorization. Editors and Admins can update and test active Integrations. Only Admins can disconnect them or rotate webhook secrets. Viewers can read permitted metadata. Investigation and Conversation permissions are separate.

Use the [session and Origin setup](/api-reference/overview#authentication). Save the relevant JSON example below in a private file, then submit it with this shared command. Set `INTEGRATION_CONFIG` to that file's name. For GitHub or installed Slack apps, use the [browser authorization flow](#authorize-github-or-slack-in-a-browser).

```bash
INTEGRATION_CONFIG=prometheus.json
curl --fail-with-body --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
  --data @"$INTEGRATION_CONFIG" "$OPENCLUSTER_URL/api/v1/integrations"
```

Use `PATCH /api/v1/integrations/{integration}` to update an existing Integration. When changing its configuration, send the complete configuration and include a replacement credential if the Integration already has one. Test the connection after changing configuration on a source without a credential. If access changes during verification and the API returns `409`, reload the Integration before retrying.

### Prometheus configuration

Save your configuration as private `prometheus.json`, then use the [shared creation command](#connect-an-integration):

```json
{
  "type": "prometheus",
  "name": "Production metrics",
  "configuration": {
    "url": "https://metrics.example.com",
    "bearerToken": "<read-only-token>"
  }
}
```

Omit `bearerToken` if your endpoint allows unauthenticated reads.

### Loki configuration

Save this example as private `loki.json`, then use the [shared creation command](#connect-an-integration):

```json
{
  "type": "loki",
  "name": "Production logs",
  "configuration": {
    "url": "https://logs.example.com",
    "auth": "bearer",
    "token": "<read-only-token>",
    "tenantId": "production"
  }
}
```

Omit `tenantId` unless Loki requires a single tenant header. For a trusted endpoint that allows unauthenticated reads, set `auth` to `none` and omit both token and username. Legacy bearer configuration without a token remains supported. For Basic authentication, including Grafana Cloud Loki, set `auth` to `basic`, add `username` from your Loki settings and use a read-only token.

### Tempo configuration

Save this example as private `tempo.json`, then use the [shared creation command](#connect-an-integration):

```json
{
  "type": "tempo",
  "name": "Production traces",
  "configuration": {
    "url": "https://traces.example.com",
    "auth": "bearer",
    "token": "<read-only-token>"
  }
}
```

Add `tenantId` if Tempo requires a single tenant header. Use `auth: basic` with a `username` and read-only token for Basic authentication, including Grafana Cloud Tempo. Omit the bearer token only for a trusted endpoint that allows unauthenticated reads.

### Kubernetes creation

Find the connected Relay ID with `GET /api/v1/relays`. Replace the Relay ID and namespace list below. After creation, request [verification](#verify-an-integration).

```bash
curl --fail-with-body --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
  --data '{
    "type": "kubernetes",
    "name": "Production cluster",
    "relayId": "<relay-id>",
    "configuration": {"namespaceAllowList": "checkout,payments"}
  }' "$OPENCLUSTER_URL/api/v1/integrations"
```

### Slack configuration

An Admin can use an existing token for read-only access without configuring the deployment's Slack installation flow. Save this as private `slack.json` and submit it with the [shared creation command](#connect-an-integration):

```json

  "name": "Operations workspace",

```

## Ask a question

With an Editor or Admin session and a configured model provider, open a Conversation:

```bash
curl --fail-with-body --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
  --data '{"subject":"Checkout health","message":"Is the checkout Deployment healthy in the payments namespace?"}' \
  "$OPENCLUSTER_URL/api/v1/conversations"
```

Save the returned `id` as `CONVERSATION_ID`. Use `GET /api/v1/conversations/{conversation}` to read its Messages and turns. A turn's `investigationId` identifies the result at `GET /api/v1/investigations/{investigation}`, including Findings and citations. Follow the [Investigation event stream](/api-reference/overview#investigation-event-streams) for live progress. Send a follow-up with `POST /api/v1/conversations/{conversation}/messages` and a body such as `{"message":"What do recent namespace Events show?"}`. Use the same cookie and Origin headers.

## Investigate an Incident

Use `GET /api/v1/incidents` to find the Incident and `GET /api/v1/investigations` to find any automatically opened Investigation. To open another Investigation intentionally:

```bash
curl --fail-with-body --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
  --data '{"incidentId":"<incident-id>"}' "$OPENCLUSTER_URL/api/v1/investigations"
```

Read `GET /api/v1/investigations/{investigation}` or follow the event stream. Progress moves from `queued` to `running`, then `concluded`, `failed`, or `cancelled`. A concluded run can remain inconclusive.

## Conversation windows and pagination

To ask about a specific interval, send both `windowFrom` and `windowUntil` when posting
a Message, or when creating a Conversation with its first Message. Use RFC3339 timestamps
with an offset. The start is inclusive and the end exclusive. The end cannot be in the
future. Values are normalized to UTC microseconds and echoed on the accepted Message and
Investigation. Invalid windows return `400` before accepting the request.

Without explicit bounds, ordinary questions cover at least the preceding 24 hours.
Incident questions retain their Incident-derived window. The first queued Message fixes
the next batch's window. Later Messages inherit it, or may supply the same normalized
bounds. Different bounds return `409`. Resend after that batch opens. Waiting or restarting
does not move an accepted window.

The Conversation API returns its first 50 turns as execution metadata, in ascending turn
order. Replies live in the ordered Message transcript. To read more,
pass `turnsNext` as `cursor` to `GET /api/v1/conversations/{conversation}/turns`.
That endpoint accepts `limit` from 1 to 200 (default 50) and returns `turns` and `next`.
Continue until `next` is null. Cursors belong to the same Organization and Conversation.
Search and selectable sorting are not supported. The recent Message tail is separate.


## Observation response details

An Editor or Admin can retrieve one Tool Run's retained observation with
`GET /api/v1/investigations/{investigation}/runs/{ordinal}/observation`.
Use the Investigation ID and one-based ordinal from the citation. A Viewer can still
read summaries and Tool Run metadata, but this observation request returns `403`.

The response includes the requested arguments, outcome, source identifiers, execution
timing, and current Integration name and type. A renamed Integration changes this display
information. It does not rewrite the retained observation or its stable identifier.

| Field | Interpretation |
| --- | --- |
| `observationText` | Exact bounded text prepared for the next model Tool result. `null` means unavailable, including older runs. An empty string means retained empty text. |
| `truncated` | The source result may be incomplete. |
| `modelClipped` | Content or arguments were omitted to fit the model or complete-observation budget, independently of source limits. |
| `windowApplied` | `true` means the adapter supplied effective bounds. `false` means known fallback bounds. `null` means older bounds are unknown. |

Preparation does not acknowledge remote provider delivery: cancellation or a provider
failure can prevent submission. Ordinary Investigation detail, lists, and activity events
omit observation bodies. Old observations are not reconstructed by rerunning queries.


## Citation references

In API results, `runRefs` names Tool Run ordinals in the containing Investigation.
Reused Findings use `evidenceRefs` pairs of `investigationId` and `toolRunOrdinal`.
Follow the referenced Investigation's detail and `runs` to resolve them. Two Investigations
can each have Run 1, so the ordinal alone cannot identify reused evidence.
Unavailable or unauthorized Investigations return the same `404`. If a cited Tool Run
has been pruned, the Finding retains its reference and detail reports a `missing_telemetry`
limitation. It does not substitute another run or claim fresh verification.


## Interpret integration availability

`status` and `verifiedAt` describe a recorded check. `toolAvailability` combines that check, recorded grants, and `disconnected`. Provider access or Relay connectivity can change afterward. DELETE disconnects an Integration, clears its saved secrets and verification, and retains historical evidence. The Installed list excludes disconnected records. Authorized detail remains readable. Reconnect requires a new Integration with fresh credentials or authorization. Enable/Disable operations and the `disabled` filter are no longer supported.

Kubernetes verification records advertised Relay capabilities. A partial set can still return `verified`, including when no query operation is available. It does not test Kubernetes RBAC. GitHub verification checks installation and repository access, not every operation's permissions. An installation with no selected repositories can still verify.

The generic `inbound` response metadata is no longer returned. For Slack replies, check the installed app, deployment signing secret, event subscriptions, channel membership, granted scopes, model configuration, and `disconnected`. Pasted tokens provide read access without installed-app mentions. `verificationNote` is transient response guidance and is not reconstructed on ordinary reads.

Investigation lifecycle is separate from assessment certainty. `queued` means waiting and `running` means assigned for execution, including interrupted work awaiting recovery. Terminal states are `concluded`, `failed`, and `cancelled`. Read `conclusionStatus`, `limitations`, `stoppedBy`, and `error` to interpret the outcome. The concluded event's payload `status` describes the assessment. Historical results may retain `verified_cause`. `concludedAt` records any terminal transition.
