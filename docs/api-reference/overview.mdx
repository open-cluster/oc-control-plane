OpenCluster serves JSON over the versioned `/api/v1` product API. The canonical contract
is `api/openapi.yaml`. Generated operation pages provide request builders, schemas,
responses, and cURL examples.

Set the base URL for your deployment:

```bash
export OPENCLUSTER_URL="https://oc.example.com"
```

## Investigation observations

Use `GET /api/v1/investigations/{investigation}/runs/{ordinal}/observation` to inspect
one cited Tool Run as an Editor or Admin. The response returns bounded prepared text and
source context. Older unavailable observations are `null`. Viewer access returns `403`.
Ordinary Investigation detail, lists, and events omit these bodies. See
[Inspect a cited observation](/concepts/investigations-and-conversations#inspect-a-cited-observation)
for clipping, timing, sensitivity, and retention semantics.

## Integration catalog

Use `GET /api/v1/integration-types` to discover registered types, their Tools, setup
capabilities, and configured counts. An omitted `tools` list means no query Tools.
`receivesWebhooks` identifies alert intake. Per-Integration `toolAvailability` reports
which Tools are currently usable.

The configuration examples below describe credential inputs. Secret inputs
are accepted during setup and never returned in configuration reads.

The pre-production catalog response no longer includes `logo`, `available`, `capabilities`,
`secretFields`, `documentationSlug`, `documentationUrl`, `productDocumentationUrl`, or
`configurationSchema`. API clients use the type key for branding, registered catalog
membership for type availability, and `tools` for operations. Setup instructions and
vendor references remain in the integration guides.

## Authentication

Use the session cookie issued by local sign-in or OIDC. Bootstrap uses its one-time deployment token. Webhooks use separate credentials.

If you completed [Docker Compose setup](/self-hosting/docker-compose), reuse its cookie jar:

```bash
export OPENCLUSTER_URL="http://localhost:8081"
export OPENCLUSTER_COOKIE=".secrets/session-cookie"
```

For an existing local account, use your deployment URL. Run `umask 077` before creating
a private `sign-in.json` file with the `email` and `password` fields. The command below
removes the password file when the request finishes, even if sign-in fails.

```bash
umask 077
export OPENCLUSTER_COOKIE="$PWD/opencluster.cookies"
(
  trap 'rm -f -- sign-in.json' EXIT
  curl --fail-with-body --cookie-jar "$OPENCLUSTER_COOKIE" \
    --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
    --data @sign-in.json "$OPENCLUSTER_URL/api/v1/auth/local/sign-in"
)
```

Treat the cookie jar as a credential. Unsafe product requests such as POST and PATCH must include `Origin` matching the configured public origin. Add the header when copying generated examples.

## Verify an Integration

Set `INTEGRATION_ID` to the ID returned during setup. An Editor or Admin can request verification:

```bash
curl --fail-with-body --request POST --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" \
  "$OPENCLUSTER_URL/api/v1/integrations/$INTEGRATION_ID/verify"
```

Use the returned `status` and `toolAvailability` for technical diagnosis. `verificationNote` may be included in verification and credential mutation responses. Ordinary reads do not reconstruct it. Query-source creation and provider authorization already probe access. Kubernetes needs this explicit check. For webhook sources, this operation reports accepted delivery history and returns `failed` when none exists. That alone does not establish an outage.

Configuration edits without replacement credentials retain existing credentials and verification state. Recheck access after changing an endpoint or tenant. Replacement credentials are probed before saving. A successful probe cannot guarantee future queries.

## Authorize GitHub or Slack in a browser

**Advanced workaround for API-only deployments.** Use your browser's developer console
to start authorization with the same browser session that receives the provider callback.

Use the deployment's public HTTPS origin. Check `supportsConnect` for the Integration type in `GET /api/v1/integration-types`.

1. Open `/healthz` on the OpenCluster origin in your browser. For OIDC, first visit `/api/v1/auth/oidc/start` on that origin and complete sign-in. For local authentication, open the browser's developer console on the OpenCluster origin and run:

   ```js
   const signIn = await fetch("/api/v1/auth/local/sign-in", {
     method: "POST",
     headers: {"Content-Type": "application/json"},
     body: JSON.stringify({
       email: prompt("OpenCluster Admin email"),
       password: prompt("OpenCluster password"),
     }),
   });
   if (!signIn.ok) throw new Error("Sign-in failed: " + signIn.status);
   ```

2. In the same browser, start setup. Replace `github` with `slack` for Slack:

   ```js
   const setup = await fetch(
     "/api/v1/integration-types/github/connect?returnTo=%2Fapi%2Fv1%2Fsession",
     {method: "POST"},
   );
   if (!setup.ok) throw new Error("Setup failed: " + setup.status);
   location.assign((await setup.json()).authorizationUrl);
   ```

3. Approve the installation at the provider and return in the same browser. The redirect goes to the session endpoint. Check its URL for `connect=connected` and the `integration` ID. Open `/api/v1/integrations/<integration-id>` on the same origin to confirm its status. If setup fails or expires, start again.

A cURL cookie jar is separate from your browser session. The callback needs the browser session that started setup.

## Organization identity

Each authenticated User belongs to one Organization. The server resolves that Organization
and Role from the current session before it serves a protected operation. You can inspect the
resolved identity with:

```bash
export ORGANIZATION_ID="$(
  curl --fail-with-body --silent \
    --cookie "$OPENCLUSTER_COOKIE" \
    "$OPENCLUSTER_URL/api/v1/session" |
  jq --raw-output '.organization.id'
)"

test -n "$ORGANIZATION_ID" && test "$ORGANIZATION_ID" != "null"
```

Then call an Organization-owned operation without supplying an Organization selector:

```bash
curl --fail-with-body \
  --cookie "$OPENCLUSTER_COOKIE" \
  "$OPENCLUSTER_URL/api/v1/incidents"
```

The Organization is never selected by a request header, body, query, or path value.

## Versioning

Public product operations use `/api/v1`. Inbound provider routes use `/webhooks/v1` and
have separate authentication, payload, and retry contracts. Health, readiness, metrics,
and Relay gRPC traffic are not part of the product OpenAPI surface.

OSS v0.1 is pre-release. Use the OpenAPI document shipped with the exact source or release
you deploy. Do not assume compatibility from a `latest` URL.

Investigation and Conversation turn statuses are `queued`, `running`, `concluded`,
`failed`, and `cancelled`. This replaces the earlier `investigating` with `running` and
maps `partial` and `needs_input` to `concluded`. Clients must read `conclusionStatus`,
limitations, and `stoppedBy` for outcomes rather than interpreting lifecycle as certainty.
Upgrade clients and server replicas together. Mixed versions may return either status
vocabulary during a rolling upgrade. No database migration is required for this change.

## Pagination

Collection operations document a bounded `limit` and an opaque cursor such as `after` or
`cursor`. Pass the returned `next` value unchanged to the parameter named by that
operation. An empty or null `next` means the collection is complete.

Do not decode a cursor or construct one from a resource ID.

## Errors

JSON errors contain a safe `error` message and may include a stable `reason` or required
Permission. Use the HTTP status and request identifier for diagnosis. Do not parse the
message text to make authorization decisions.

| Status | Meaning | Client action |
| --- | --- | --- |
| `400` | Invalid request | Correct the request. Do not retry it unchanged. |
| `401` | Missing or rejected authentication | Sign in again or correct the route-specific credential. |
| `403` | Insufficient Permission | Request the required Role. Changing the Organization ID does not grant access. |
| `404` | Unknown or inaccessible resource | Do not use the response to infer another Organization's data. |
| `409` | State conflict | Refresh the resource and resolve the conflicting state. |
| `429` | Rate limited | Retry after `Retry-After` when present. |
| `503` | Temporarily unavailable | Retry with bounded backoff. |

Responses containing Organization data use `Cache-Control: no-store`.

## Webhooks

The canonical alert path is
`POST /webhooks/v1/integrations/{integration}/alert-events`. The Integration selects the
provider adapter. Generic Webhook and Alertmanager use the one-time
`X-OpenCluster-Token`. Slack uses its signed provider request.

`202 Accepted` means a delivery is durable, and an exact retry of an accepted lifecycle
phase returns `200 OK`. Correct `400`, `401`, and `413` responses before retrying. Alert
webhooks use `503` for temporary admission pressure so Alertmanager retries them. Retry with
bounded backoff and honor `Retry-After` when present. Slack admission pressure remains `429`.

Use [Generic Webhook](/integrations/alerting/generic_webhook) or
[Prometheus Alertmanager](/integrations/alerting/alertmanager) for sender setup. Alert
deliveries finish during admission. Admins can recover terminal Slack processing
by Conversation and Message sequence through the Slack recovery operation.

## Investigation event streams

Investigation activity uses increasing sequence identifiers. SSE clients reconnect with
`Last-Event-ID`. Comment frames are heartbeats and carry no product event. Store the last
processed sequence only after handling its event successfully.

Streams send an idle heartbeat every 15 seconds and can stay open beyond ordinary HTTP
request timeouts. Each event batch has a 10-second write deadline. A stalled connection
is dropped and can reconnect using its last processed sequence. Streams close on a terminal
event, an already processed terminal cursor, or server shutdown. Reconnect after shutdown
to resume from durable activity.

Reverse proxies must disable response buffering and allow at least 60 seconds between
upstream reads. The supplied nginx configuration uses `proxy_buffering off`,
`proxy_read_timeout 60s`, and `send_timeout 10s` to bound stalled downstream clients.

Terminal events are `concluded`, `failed`, and `cancelled`. Ignore an unknown future event
type while retaining its envelope so a newer server remains compatible with an older
client. The generated stream operation documents the seven currently shipped event
payloads: started, progress, Tool started, Tool completed, concluded, failed, and cancelled.
These payloads carry operational display data only. Hypotheses appear in the final
Investigation conclusion. A refused unavailable Tool is reported as a failed read without
claiming it started against an Integration.

Browse the [API surface](/api-reference/surface) or select an individual generated
method/path entry in the navigation.

## Connect an Integration

An Admin creates Integrations or starts provider authorization. Editors and Admins can update, enable, disable, and verify existing Integrations. Only Admins can delete them or rotate webhook secrets. Viewers can read permitted metadata. Investigation and Conversation permissions are separate.

Use the session and Origin setup above. Configuration files contain credentials and must remain private. Send the complete configuration when updating it. For GitHub or installed Slack apps, use the [browser authorization flow](#authorize-github-or-slack-in-a-browser).

### Prometheus configuration

Use the [API session and Origin setup](/api-reference/overview#authentication). Save your configuration in a private file named `prometheus.json`:

```json
{
  "type": "prometheus",
  "name": "Production metrics",
  "configuration": {
    "url": "https://metrics.example.com",
    "bearerToken": "<read-only-token>"
  }
}
```

Omit `bearerToken` if your endpoint allows unauthenticated reads.

```bash
curl --fail-with-body --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
  --data @prometheus.json "$OPENCLUSTER_URL/api/v1/integrations"
```

### Loki configuration

Use the [API session and Origin setup](/api-reference/overview#authentication). Save this example as a private `loki.json` file:

```json
{
  "type": "loki",
  "name": "Production logs",
  "configuration": {
    "url": "https://logs.example.com",
    "auth": "bearer",
    "token": "<read-only-token>",
    "tenantId": "production"
  }
}
```

Omit `tenantId` unless Loki requires a single tenant header. Omit the token only for a trusted endpoint that allows unauthenticated reads. For Basic authentication, including Grafana Cloud Loki, set `auth` to `basic`, add `username` from your Loki settings and use a read-only token.

```bash
curl --fail-with-body --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
  --data @loki.json "$OPENCLUSTER_URL/api/v1/integrations"
```

## Ask a question

With an Editor or Admin session and a configured model provider, open a Conversation:

```bash
curl --fail-with-body --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
  --data '{"subject":"Checkout health","message":"Are checkout pods healthy in the payments namespace?"}' \
  "$OPENCLUSTER_URL/api/v1/conversations"
```

Save the returned `id` as `CONVERSATION_ID`. Read the Conversation to follow its Messages and turns. Send a follow-up with `POST /api/v1/conversations/{conversation}/messages` and a body such as `{"message":"What do recent namespace Events show?"}`. Use the same cookie and Origin headers.

## Investigate an Incident

Use `GET /api/v1/incidents` to find the Incident and `GET /api/v1/investigations` to find any automatically opened Investigation. To open another Investigation intentionally:

```bash
curl --fail-with-body --cookie "$OPENCLUSTER_COOKIE" \
  --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
  --data '{"incidentId":"<incident-id>"}' "$OPENCLUSTER_URL/api/v1/investigations"
```

Read `GET /api/v1/investigations/{investigation}` or follow the event stream. Progress moves from `queued` to `running`, then `concluded`, `failed`, or `cancelled`. A concluded run can remain inconclusive.
