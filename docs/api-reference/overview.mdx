OpenCluster serves JSON over the versioned `/api/v1` product API. The canonical contract
is `api/openapi.yaml`. Generated operation pages provide request builders, schemas,
responses, and cURL examples.

Set the base URL for your deployment:

```bash
export OPENCLUSTER_URL="https://oc.example.com"
```

## Authentication

Use the session cookie issued by initial local signup, local sign-in, or OIDC. Webhooks use separate credentials.

For command-line access with an existing account, choose your deployment URL and a private cookie-jar path:

```bash
export OPENCLUSTER_URL="http://localhost:8081"
export OPENCLUSTER_COOKIE=".secrets/session-cookie"
```

For an existing local account, use your deployment URL. Run `umask 077` before creating
a private `sign-in.json` file with the `email` and `password` fields. The command below
removes the password file when the request finishes, even if sign-in fails.

```bash
umask 077
export OPENCLUSTER_COOKIE="$PWD/opencluster.cookies"
(
  trap 'rm -f -- sign-in.json' EXIT
  curl --fail-with-body --cookie-jar "$OPENCLUSTER_COOKIE" \
    --header "Origin: $OPENCLUSTER_URL" --header 'Content-Type: application/json' \
    --data @sign-in.json "$OPENCLUSTER_URL/api/v1/auth/local/sign-in"
)
```

Treat the cookie jar as a credential. Unsafe product requests such as POST and PATCH must include `Origin` matching the configured public origin. Add the header when copying generated examples.

## Organization identity

Each authenticated User belongs to one Organization. The server resolves that Organization
and Role from the current session before it serves a protected operation. You can inspect the
resolved identity with:

```bash
export ORGANIZATION_ID="$(
  curl --fail-with-body --silent \
    --cookie "$OPENCLUSTER_COOKIE" \
    "$OPENCLUSTER_URL/api/v1/session" |
  jq --raw-output '.organization.id'
)"

test -n "$ORGANIZATION_ID" && test "$ORGANIZATION_ID" != "null"
```

Then call an Organization-owned operation without supplying an Organization selector:

```bash
curl --fail-with-body \
  --cookie "$OPENCLUSTER_COOKIE" \
  "$OPENCLUSTER_URL/api/v1/incidents"
```

The Organization is never selected by a request header, body, query, or path value.

## Versioning

Public product operations use `/api/v1`. Inbound provider routes use `/webhooks/v1` and
have separate authentication, payload, and retry contracts. Health, readiness, metrics,
and Relay gRPC traffic are not part of the product OpenAPI surface.

OSS v0.1 is pre-release. Use the OpenAPI document shipped with the exact source or release
you deploy. Do not assume compatibility from a `latest` URL.

Investigation and Conversation turn statuses are `queued`, `running`, `concluded`,
`failed`, and `cancelled`. This replaces the earlier `investigating` with `running` and
maps `partial` and `needs_input` to `concluded`. Clients must read `conclusionStatus`,
limitations, and `stoppedBy` for outcomes rather than interpreting lifecycle as certainty.
Upgrade clients and server replicas together. Mixed versions may return either status
vocabulary during a rolling upgrade. No database migration is required for this change.

## Pagination

Collection operations document a bounded `limit` and an opaque cursor such as `after` or
`cursor`. Pass the returned `next` value unchanged to the parameter named by that
operation. An empty or null `next` means the collection is complete.

Do not decode a cursor or construct one from a resource ID.

## Errors

JSON errors contain a safe `error` message and may include a stable `reason` or required
Permission. Use the HTTP status and request identifier for diagnosis. Do not parse the
message text to make authorization decisions.

| Status | Meaning | Client action |
| --- | --- | --- |
| `400` | Invalid request | Correct the request. Do not retry it unchanged. |
| `401` | Missing or rejected authentication | Sign in again or correct the route-specific credential. |
| `403` | Insufficient Permission | Request the required Role. Changing the Organization ID does not grant access. |
| `404` | Unknown or inaccessible resource | Do not use the response to infer another Organization's data. |
| `409` | State conflict | Refresh the resource and resolve the conflicting state. |
| `429` | Rate limited | Retry after `Retry-After` when present. |
| `503` | Temporarily unavailable | Retry with bounded backoff. |

Responses containing Organization data use `Cache-Control: no-store`.

## Webhooks

The canonical alert path is
`POST /webhooks/v1/integrations/{integration}/alert-events`. The Integration selects the
provider adapter. Generic Webhook and Alertmanager use the one-time
`X-OpenCluster-Token`. Slack uses its signed provider request.

`202 Accepted` means a delivery is durable, and an exact retry of an accepted lifecycle
phase returns `200 OK`. Correct `400`, `401`, and `413` responses before retrying. Alert
webhooks use `503` for temporary admission pressure so Alertmanager retries them. Retry with
bounded backoff and honor `Retry-After` when present. Slack admission pressure remains `429`.

For full request schemas, select `POST /webhooks/v1/integrations/{integration}/alert-events` under **Endpoints**. The request schema includes both Generic Webhook and Alertmanager bodies.

Use [Generic Webhook](/integrations/alerting/generic_webhook) or
[Prometheus Alertmanager](/integrations/alerting/alertmanager) for sender setup. Alert
deliveries finish during admission. Admins can recover terminal Slack processing
by Conversation and Message sequence through the Slack recovery operation.

## Investigation event streams

Investigation activity uses increasing sequence identifiers. SSE clients reconnect with
`Last-Event-ID`. Comment frames are heartbeats and carry no product event. Store the last
processed sequence only after handling its event successfully.

Streams send an idle heartbeat every 15 seconds and can stay open beyond ordinary HTTP
request timeouts. Each event batch has a 10-second write deadline. A stalled connection
is dropped and can reconnect using its last processed sequence. Streams close on a terminal
event, an already processed terminal cursor, or server shutdown. Reconnect after shutdown
to resume from durable activity.

Reverse proxies must disable response buffering and allow at least 60 seconds between
upstream reads. The supplied nginx configuration uses `proxy_buffering off`,
`proxy_read_timeout 60s`, and `send_timeout 10s` to bound stalled downstream clients.

Terminal events are `concluded`, `failed`, and `cancelled`. Ignore an unknown future event
type while retaining its envelope so a newer server remains compatible with an older
client. The generated stream operation documents the seven currently shipped event
payloads: started, progress, Tool started, Tool completed, concluded, failed, and cancelled.
These payloads carry operational display data only. Hypotheses appear in the final
Investigation conclusion. A refused unavailable Tool is reported as a failed read without
claiming it started against an Integration.

Select an operation under **Endpoints**. For examples, see [API workflows](/api-reference/workflows).
