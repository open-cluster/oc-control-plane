An Investigation is one immutable evidence-gathering turn. It moves through `queued` and
`running`, then ends as `concluded`, `cancelled`, or `failed`. `queued` means waiting for
execution; `running` means assigned to a worker. Interrupted execution remains `running`
until failure recovery completes. `concluded` means execution completed, including an
inconclusive assessment or a request for human input.

Read `conclusionStatus`, `limitations`, `stoppedBy`, and `error` separately to understand
the result. A `concluded` event's payload `status` describes assessment certainty;
it is not the Investigation lifecycle status.

The first activity event explains that OpenCluster is reviewing the request and available
evidence sources. It does not mean a source has already been read. Older recorded startup
events may have no explanatory text; their replay remains supported.
Tool completion activity follows a recorded Tool Run. If recording fails, the Investigation
cannot use that result as evidence or report its completion.
When several eligible Integrations offer the same operation, OpenCluster selects the source
explicitly from the connected sources it may read. With one eligible source, selection is
automatic. The Tool Run records which Integration supplied the result.

## Conversations and follow-ups

A Conversation is the ordered context a person talks to. Each Message may open a new Investigation. Follow-ups reuse bounded prior Findings and citations without copying raw provider payloads or private model reasoning.

Recent context includes up to 12 user and assistant Messages, oldest first, with their
timestamps. Only Messages owned by earlier Investigations are included; current and
queued requests remain separate. A previous reply is retained even if it arrived after
the current request was queued. Recent replies provide compact text; their structured
details, including Action Proposals and citations, are available on demand.
Another Conversation's private answers are not included. Long entries are shortened and
marked as truncated. This bounded context is not a complete memory of the Conversation.
When recent context is insufficient, the investigator can read bounded older pages from
the same Conversation. Those pages preserve Message order, corrections, canonical answers,
and their Investigation identities. Stored history is context rather than a current request
or fresh evidence. Prior Findings retain their observation time and evidence window and can
be reconsidered after a correction, refresh request, or window change.
Initial Findings, including those shared through the same Incident, must have been
concluded before the current Investigation opened. Later evidence enters through explicit
reads rather than silently changing prior context.

Completed Investigations never resume, including those requiring human input. Send a new
Message to create the next turn.

To ask about a specific interval, send both `windowFrom` and `windowUntil` when posting
a Message, or when creating a Conversation with its first Message. Use RFC3339 timestamps
with an offset. The start is inclusive and the end exclusive; the end cannot be in the
future. Values are normalized to UTC microseconds and echoed on the accepted Message and
Investigation. Invalid windows return `400` before accepting the request.

Without explicit bounds, ordinary questions cover at least the preceding 24 hours;
Incident questions retain their Incident-derived window. The first queued Message fixes
the next batch's window. Later Messages inherit it, or may supply the same normalized
bounds. Different bounds return `409`; resend after that batch opens. Waiting or restarting
does not move an accepted window.

The Conversation API returns its first 50 turns as execution metadata, in ascending turn
order. Replies live in the ordered Message transcript. To read more,
pass `turnsNext` as `cursor` to `GET /api/v1/conversations/{conversation}/turns`.
That endpoint accepts `limit` from 1 to 200 (default 50) and returns `turns` and `next`.
Continue until `next` is null. Cursors belong to the same Organization and Conversation;
search and selectable sorting are not supported. The recent Message tail is separate.

The structured Conclusion, assistant Message, and final activity event are saved together,
so reconnecting sees the same outcome. Failed final writes do not report a completed reply.
An interrupted or superseded worker cannot append results or activity after losing ownership.

Messages sent during an active Investigation wait for its completion. An Organization can
have up to 100 unassigned user Messages waiting across its Conversations, alongside the
separate limit for waiting Investigations. When capacity is full, new Messages are refused;
retry after work progresses. Accepted Messages remain stored. Older backlogs larger than
the limit drain in chronological batches of at most 100.

Each Investigation receives the complete Messages assigned to it, in order, with their
authors and timestamps. Those assigned user Messages are the authoritative request; there
is no separate stored question preview.
Normal requests retain their existing context. After an actual provider context rejection,
one bounded recovery can omit optional inventory and prior context while preserving current
Messages, history access and completed Tool exchanges. Omitted observations must be retrieved
again before they can support Findings.
If the complete assigned request still cannot fit after one bounded recovery attempt, the
Investigation is `failed` with a technical error. Its Messages remain stored. A capacity
error does not mean human information is missing or that the request was answered.

For example, “Why did checkout latency rise?” opens one Investigation. “Does the deploy
at 09:42 explain it?” becomes a new Message and a new bounded Investigation in the same
Conversation, retaining prior cited Findings without changing the first result.

An Investigation can remain inconclusive when access, telemetry, time, or execution bounds
prevent a defensible answer.

## Findings and citations

A Finding is a factual statement supported by one or more numbered Tool Runs. Its kind
is `cause`, `contributing_factor`, `observation`, or `ruled_out`. A causal Finding must
explain the mechanism that produced impact. Conclusion status expresses assessment
certainty; Findings do not carry a second confidence classification.

Investigations represent other uncertainty as hypotheses or limitations instead.

Final hypotheses are `supported`, `ruled_out`, or `unresolved`. Supported is weaker than
verified. Limitations name missing access, telemetry, contradictions,
unresolved assumptions, or essential human input.

Citations show what OpenCluster read, not that the source was complete or correct. Check
source timestamps, bounded windows, contradictions, and truncation before accepting a
Finding.

A Finding must cite successful reads. Failed or skipped reads can explain limitations,
but cannot establish an observation or cause. A skipped duplicate refers to the original
read rather than creating another observation. Prior citations must still resolve to
available successful reads in the same Organization.

The investigator may repeat a read to refresh changing infrastructure or retry a failed
source within the execution limits. Identical reads requested together execute once;
each Tool Run states whether the read executed or was skipped. A descriptive purpose is
optional metadata and does not grant access.

In API results, `runRefs` names Tool Run ordinals in the containing Investigation.
Reused Findings use `evidenceRefs` pairs of `investigationId` and `toolRunOrdinal`;
follow the referenced Investigation's detail and `runs` to resolve them. Two Investigations
can each have Run 1, so the ordinal alone cannot identify reused evidence.
Unavailable or unauthorized Investigations return the same `404`. If a cited Tool Run
has been pruned, the Finding retains its reference and detail reports a `missing_telemetry`
limitation; it does not substitute another run or claim fresh verification.

## Action Proposals

An Action Proposal can describe mitigation, rollback, verification, a permanent fix, or
monitoring. It states a rationale, verification procedure, and supporting Tool Runs.
OpenCluster never executes it.

Accepted summaries and Action Proposals retain their complete text. Oversized output is
returned for a bounded correction; if no valid Conclusion can be produced, the Investigation
fails instead of silently shortening an operational recommendation.

For example, a rollback proposal may cite a Kubernetes Event and a GitHub deployment,
and explain how to verify latency and error rate afterward. The citations support the
proposal; they do not execute or approve the change.

## Postmortems

A Postmortem belongs to one resolved Incident. A person triggers generation; OpenCluster
does not create one automatically. The draft distinguishes system evidence from
Conversation testimony and remains `draft` until reviewed.

Missing impact, resolution, owner, or deadline facts appear as `Needs human input.` rather
than being invented. A correction creates a new revision, and review records the reviewer
without turning testimony into system evidence. Postmortems remain nested under Incidents
in OSS v0.1 and are not automatically published.

Use [Run your first investigation](/getting-started/run-your-first-investigation) for the
end-to-end procedure.
