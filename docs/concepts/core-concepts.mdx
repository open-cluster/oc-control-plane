A Conversation is where you ask operational questions and follow up on answers. Start one through Slack or the Conversation API, with or without an incident.

An Investigation gathers evidence to answer a question or explain an incident. OpenCluster reads connected systems, reports findings with citations, and identifies what remains unknown. Follow-ups start new investigations while retaining useful context from earlier answers.

## Connected sources

An Integration gives OpenCluster access to a configured system. Some provide evidence, some accept alerts, and Slack also provides conversational interaction. Provider permissions determine what OpenCluster can read.

For Kubernetes, Relay performs reads inside your environment. Cluster credentials remain there. See [Integrations](/integrations/overview) to choose sources.

## How the records relate

An Alert Event is an alert received from a connected sender. Firing and resolved alerts create or update an Incident using the sender's grouping identity. An incident resolves when none of its grouped alerts are firing.

Grouping does not establish a shared cause. Several alerts can belong to one incident even when they have different causes. An investigation checks the evidence for an explanation.

For example, an Alertmanager delivery can open an incident about checkout errors. OpenCluster can read Kubernetes workload state and GitHub changes to investigate it. You can also ask about checkout directly, without waiting for an alert.

## Results and access

A Finding states what the evidence supports. Citations identify the reads behind it. An Action Proposal recommends a next step for human review. After an incident resolves, you can generate and review a draft Postmortem.

Your Organization controls access to OpenCluster data through Admin, Editor, and Viewer roles. Provider access adds its own limits. Missing telemetry, incomplete results, and old observations can limit an answer even when a source is connected.
