<Warning>
  The chart at `deploy/helm/opencluster` is not a complete OpenCluster installation. It
  deploys the control plane only. You must supply PostgreSQL, ingress, and TLS
  termination. A separately deployed browser console is optional and needs same-origin routing.
</Warning>

## Prerequisites

You need Kubernetes, Helm 3, a reachable PostgreSQL database, outbound HTTPS access to
the selected model provider, and two Secrets:

- `opencluster-database` with key `postgres-dsn`.
- `opencluster-credentials` with keys `sealing-key` and `model-key`.

The encryption key must be exactly 32 bytes. Do not put credentials in Helm values or
command history. Initial signup uses private deployment access rather than an administrator
token. The first caller to reach an empty installation can claim its Admin account.

## Install

For a new installation, create a values file with the released image, model provider,
and model. Keep the deployment inaccessible to untrusted workloads until signup:

`server.publicURL` is required and must match the browser origin. During setup, use a
separately supplied frontend on workstation loopback with a same-origin `/api/` proxy to
the port-forwarded backend. The example uses frontend `http://localhost:8080` and backend
`http://127.0.0.1:8081`. Both must remain private.

```yaml
image:
  repository: IMAGE_REPOSITORY
  tag: VERSION
  pullPolicy: IfNotPresent
server:
  publicURL: http://localhost:8080
model:
  provider: anthropic
  name: MODEL_ID
database:
  existingSecret: opencluster-database
credentials:
  existingSecret: opencluster-credentials
```

Install from a checkout of the matching release:

```bash
helm upgrade --install opencluster ./deploy/helm/opencluster \
  --namespace opencluster --create-namespace --values values.yaml
kubectl --namespace opencluster rollout status deployment/opencluster-opencluster
```

## Create the first account privately

The chart's default ClusterIP Service is not internet-facing, but other Pods in the
cluster may still be able to reach it. Restrict service and Pod access using your
existing Kubernetes network controls until the first Admin is created. Do not enable
public ingress, NodePort, or LoadBalancer exposure during initial signup.

Use Kubernetes-authenticated port-forwarding bound to workstation loopback:

```bash
kubectl --namespace opencluster port-forward --address 127.0.0.1 deployment/opencluster-opencluster 8081:8081
```

With a compatible frontend and private same-origin `/api/` proxy, open
`http://localhost:8080/setup` and create the initial Admin. This repository does
not supply that frontend. The existing bootstrap API also supports a localhost
request as documented in [Compose](/self-hosting/docker-compose#3-create-the-first-user-and-organization).

Bootstrap creates the Organization, password, Membership, audit record, and secure
session atomically. The frontend can call `GET /api/v1/session` immediately. No setup
flag, token, additional login, or separate setup endpoint is required.

## Publish after initialization

After confirming the Admin exists, change `server.publicURL` to the final HTTPS browser
origin and upgrade the Deployment before enabling public ingress. Normal HTTP probes
remain active throughout. Configure the public proxy to preserve Origin and cookie
attributes. Sign in again at the final hostname because localhost cookies do not
transfer across hosts.

If the database is reset or replaced, protect the installation again before it can
accept traffic. An empty database permits first-user registration.

## Verify

The rollout proves only that the control-plane component is ready. The installation is
usable only after ingress routes `/api/v1`, `/webhooks/v1`,
`/healthz`, and `/readyz` to the HTTP Service on the configured public origin. Verify both
probes through that route:

```bash
curl --fail https://YOUR-OPENCLUSTER/healthz
curl --fail https://YOUR-OPENCLUSTER/readyz
```

Both commands must succeed before the deployment accepts user traffic.

## Optional Relay listener

Set `relay.enabled=true`, provide at least one `relay.spkiPins` value, and name a TLS
Secret in `relay.tls.existingSecret`. The Secret must contain the configured certificate
and private-key keys. Expose the Relay port only to customer Relays. They initiate the
connection and pin the control-plane public key.

## Resources and upgrades

The chart intentionally ships no generic CPU or memory requests. Set requests and limits
from measured Investigation concurrency and provider workloads before production. OSS
v0.1 does not publish a qualified in-place upgrade path. Do not infer compatibility from
image or chart tags. See [Feature availability](/feature-availability).

Back up PostgreSQL, disable any autoscaler that could restart old replicas, scale the old
Deployment to zero, and wait for every old Pod to terminate. Do not use a rolling upgrade
or run mixed versions against one database. Remove obsolete administrator token inputs,
`credentials.bootstrapTokenKey`, and any `security.bootstrapTokenFile` YAML setting.
Retain the existing database, encryption key, and other credentials. Existing accounts
and sessions need no signup-specific schema migration or reset. Relay
credentials are unchanged. The current ledgered baseline migrates only
when retained user Message attribution agrees with each Conversation source, every
retained nonempty Investigation question has assigned user Messages, and any nonempty
Postmortem reviewer is the UUID of an existing User. A failed check rolls back the migration
without changing the old schema. Repair the data with the old version or restore the backup
before retrying. Unknown or unledgered pre-release schemas still
require a fresh application database and complete setup.

Update API clients before the new Pods start. Conversations now expose `source` (`web` or
`slack`) instead of `surface` and have no lifecycle `state`. Message roles are `user` and
`assistant`, attribution uses `authorId` and `authorName`, and replies are assistant Messages
rather than Turn answers. Final hypotheses have no ID or `exploring` status. Investigation event envelopes use
`schemaVersion: 2` with seven compact payloads.

## Common failure and recovery

If the rollout stalls, inspect
`kubectl --namespace opencluster describe deployment/opencluster-opencluster` and the
control-plane Pod logs. Correct missing Secret keys, database reachability, or model
provider configuration, then rerun the Helm command. A ready Pod does not compensate for
missing ingress or TLS routing.
