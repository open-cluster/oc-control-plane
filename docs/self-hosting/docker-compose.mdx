description: "Run the complete OSS deployment with PostgreSQL, mounted secret files, and health checks."

Docker Compose is the shortest complete self-hosted path. The checked-in stack runs the
control plane and PostgreSQL, publishing the API on `127.0.0.1:8081`. It does not include
a browser console. Visiting `/` returns `404`.

## Prerequisites

You need Git, Docker Compose, curl, OpenSSL, port `8081`, and outbound HTTPS access to Anthropic or OpenRouter. Have a provider API key and a Tool-calling model identifier ready. The commands below use a POSIX shell. The repository does not publish qualified minimum hardware requirements.

Use a patched Docker Engine 28.0.0 or newer for the
[localhost-port isolation fixes](https://docs.docker.com/engine/network/port-publishing/#publishing-ports).
During initial signup,
keep the backend private from other hosts, untrusted containers, and public proxies.
A fresh or reset database allows its first caller to claim the administrator account.

## 1. Create local secret files

From a checkout of the release you intend to deploy, create private files outside version control for the PostgreSQL
password, PostgreSQL DSN, 32-byte encryption key, and model
provider credential. The four `*_FILE` variables below name credential files. The remaining variables
select the provider, model, and container user.

On Linux or macOS, create the files and export the Compose inputs. Replace the obvious
placeholders. The password in the DSN must be URL-encoded and equal the PostgreSQL
password file.

```bash
install -d -m 700 .secrets
printf '%s' '<POSTGRES_PASSWORD>' > .secrets/postgres-password
printf '%s' 'postgresql://opencluster:<URL_ENCODED_PASSWORD>@postgres:5432/opencluster?sslmode=disable' > .secrets/postgres-dsn
openssl rand -out .secrets/encryption-key 32
printf '%s' '<MODEL_API_KEY>' > .secrets/model-key
chmod 600 .secrets/*

export OPENCLUSTER_POSTGRES_PASSWORD_FILE="$PWD/.secrets/postgres-password"
export OPENCLUSTER_DATABASE_DSN_FILE="$PWD/.secrets/postgres-dsn"
export OPENCLUSTER_ENCRYPTION_KEY_FILE="$PWD/.secrets/encryption-key"
export OPENCLUSTER_AI_API_KEY_FILE="$PWD/.secrets/model-key"
export OPENCLUSTER_AI_PROVIDER=anthropic
export OPENCLUSTER_AI_MODEL='<MODEL_ID>'
export OPENCLUSTER_RUNTIME_UID="$(id -u)"
export OPENCLUSTER_RUNTIME_GID="$(id -g)"
```

OpenRouter users set `OPENCLUSTER_AI_PROVIDER=openrouter` and an exact model identifier
such as `z-ai/glm-4.7`. The model must support Tool calling and have an endpoint that
satisfies OpenCluster's zero-retention policy. See [model configuration](/self-hosting/configuration#model-provider).
Docker Desktop users without `id` can set both runtime values to an available numeric
non-root ID such as `1000`.

## 2. Start OpenCluster privately

The control-plane API is published at `127.0.0.1:8081`. Keep this listener and any
frontend proxy inaccessible to untrusted callers until the first Admin exists. For
the API-only procedure below, use the default `OPENCLUSTER_PUBLIC_URL=http://localhost:8081`.
Start Compose using its single base file:

```bash
docker compose -f deploy/compose/compose.yaml up --build -d
docker compose -f deploy/compose/compose.yaml ps
curl --fail http://localhost:8081/healthz
curl --fail http://localhost:8081/readyz
```

PostgreSQL should be healthy and the control plane running. The backend does not
ship a browser console. If a container exits, inspect its Compose logs.

## 3. Create the first User and Organization

With a compatible, privately served frontend, open `/setup` and submit Organization
name, email, optional display name, and password. Ensure `OPENCLUSTER_PUBLIC_URL`
matches the browser-facing origin of its same-origin API proxy.

For the shipped API-only deployment, you can also initialize directly on localhost:

```bash
umask 077
curl --fail-with-body --request POST http://localhost:8081/api/v1/auth/local/bootstrap \
  --header 'Origin: http://localhost:8081' \
  --header 'Content-Type: application/json' \
  --cookie-jar .secrets/session-cookie \
  --data '{"organizationName":"Platform Team","email":"admin@example.com","password":"<STRONG_PASSWORD>"}'
curl --fail --cookie .secrets/session-cookie http://localhost:8081/api/v1/session
```

Keep passwords and the cookie jar private. Browser signup issues the same secure session
cookie and does not need a second sign-in. The first successful request initializes the
Organization and Admin atomically. Further signup requests return `409`.

## 4. Public deployment

Do not expose an empty database to the internet or other untrusted workloads. Once the
Admin is created, configure `OPENCLUSTER_PUBLIC_URL` for the final HTTPS browser origin,
recreate the backend with the same Compose file, and enable a trusted reverse proxy.
Keep the host API port loopback-bound and preserve Origin and cookie attributes.

If the database is lost or replaced, restore its backup privately before exposing the
application again. An empty database reopens first-user signup. A localhost cookie does
not transfer to a different public hostname, so sign in again at the final origin.

## Persistence and shutdown

PostgreSQL stores durable product state in the named `postgres_data` volume. A normal
restart or this shutdown command retains it:

```bash
docker compose -f deploy/compose/compose.yaml down
```

Adding `--volumes` deletes that local database. Back up PostgreSQL and retain custody of
the encryption key before moving or rebuilding a production deployment. Without the
same key, sealed integration credentials cannot be opened.

## Replace an older pre-release deployment

Stop every old control-plane replica and back up PostgreSQL before replacing the image.
Remove the obsolete administrator token inputs and any `security.bootstrapTokenFile` YAML
setting. Retain the database and encryption key. Existing accounts and sessions remain
valid, and no signup migration or database reset is required. Relay enrollment credentials are unchanged.

Do not run mixed versions against one database. The current ledgered baseline migrates in
place only when retained user Message attribution agrees with each Conversation source and
every retained nonempty Investigation question has assigned user Messages. Any nonempty
retained Postmortem reviewer must also be the UUID of an existing User. If a check fails,
startup refuses the migration and leaves the old schema unchanged. Repair the data with the
old version or restore the backup before retrying.

Unknown or unledgered pre-release schemas are still refused before mutation and require a
fresh application database. Removing the `postgres_data` volume deletes retained history,
Organizations, Users, Integrations, and credentials, so complete setup again after starting
the new version. Do not delete individual rows merely to force startup.

This migration changes the API contract: Conversations expose `source` (`web` or `slack`)
instead of `surface` and no lifecycle `state`. Message roles are `user` and `assistant`,
Message attribution uses `authorId` and `authorName`, and replies are assistant Messages
rather than Turn answers. Final hypotheses have no ID or `exploring` status. Investigation event
envelopes use `schemaVersion: 2` with the seven payloads documented in the API reference.
Update clients before bringing the new replicas online.

## Failure states

- If PostgreSQL stays unhealthy, verify that the password file and DSN agree and that
  the DSN uses host `postgres`.
- If the control plane exits, inspect
  `docker compose -f deploy/compose/compose.yaml logs control-plane` for a missing file,
  invalid key length, or provider configuration error.
- If `/healthz` works but `/readyz` fails, inspect PostgreSQL connectivity and service
  logs before accepting traffic.
- If the API is unreachable, confirm that port `8081` is free and the `control-plane`
  service is running.
