title: "Configuration"
description: "Configure OpenCluster with one YAML file and targeted overrides."

OpenCluster reads one nested YAML file and validates it before starting. Values are resolved
in this order, with later sources taking precedence:

1. Built-in defaults
2. The YAML file named by `--config` or `OC_CONFIG_FILE`
3. Environment-variable compatibility overrides
4. The `--server-address` local-development override

Do not put credentials in YAML or environment values. Settings ending in `_file` name a
mounted file containing the secret. A Kubernetes Secret, Vault agent, External Secrets
Operator, or cloud secret manager can project that file without OpenCluster embedding its
client. Production configuration does not accept secret values from the environment.

## YAML configuration

This is the smallest configuration that starts OpenCluster. Every Organization uses this
database, while `org_id` remains the tenant boundary for every durable record.

```yaml
server:
  address: ":8080"

database:
  dsn_file: "/run/secrets/postgres-dsn"

telemetry:
  service_name: "oc-control-plane"
  otlp_endpoint: ""
```

Optional settings use the same nested structure:

```yaml
server:
  operator_address: ":8080"
  intake_address: ":8080"
  public_url: "https://opencluster.example.com"
  console_url: "https://console.opencluster.example.com"
  intake_public_url: "https://intake.opencluster.example.com"
  allowed_origins: ["https://console.opencluster.example.com"]
  shutdown_timeout: "15s"

authentication:
  mode: "local"
  legacy_migration_complete: false
  bootstrap_token_file: "/run/secrets/operator-token"
  bootstrap_organization: "example-org"
  bootstrap_role: "admin"
  sealing_key_id: "current"
  sealing_key_file: "/run/secrets/sealing-key"
  previous_sealing_key_files:
    prior: "/run/secrets/prior-sealing-key"
  oidc:
    issuer: "https://identity.example.com"
    client_id: "opencluster"
    client_secret_file: "/run/secrets/oidc-client-secret"

relay:
  address: ":8443"
  spki_pins: ["BASE64_SHA256_SPKI"]
  inventory_interval: "5m"
  minimum_version: ""

model:
  provider: "anthropic"
  name: "MODEL_ID"
  api_key_file: "/run/secrets/model-key"
  effort: "high"
  consented_providers: ["anthropic"]
  base_url: ""
  spend_ceiling_cents: 500
  context_window: 128000

investigations:
  window_lead: "2h"
  max_tool_runs: 30
  max_turns: 20

conversations:
  enabled: false
  max_concurrent_investigations: 4
  max_waiting_investigations: 16
  context_threshold_percent: 50

change_ledger:
  retention_days: 90

providers:
  slack:
    api_url: ""
    client_id: ""
    client_secret_file: ""
    signing_secret_file: ""
    agent_organizations: []
  github:
    app_id: ""
    app_private_key_file: ""
    api_url: ""
    app_slug: ""
    client_id: ""
    client_secret_file: ""
    web_url: ""

telemetry:
  service_name: "oc-control-plane"
  otlp_endpoint: "collector.example.com:4317"
```

Unknown keys and additional YAML documents refuse startup. This prevents a misspelled setting
from being silently ignored. When the same setting appears in YAML and an environment variable,
the environment value wins. `--server-address` overrides both for local development.

### Rotate the sealing key

First roll out this release to every replica while the existing key remains active. Do not
start a rotation while an older replica can still write version-1 envelopes.

Give the new key a new `authentication.sealing_key_id` and point `sealing_key_file` at its
mounted file. Put every key that may still have encrypted Integration credentials under
`previous_sealing_key_files`, keyed by its former ID. OpenCluster reads old envelopes and
rewraps credentials in bounded database batches under the active key; fingerprints do not
change. Roll the new keyring configuration to every replica. Keep each previous key mounted
until all replicas report that rotation completed, then remove that map entry and restart.

Existing credentials written before key IDs were introduced use the implicit `default` key ID.
During the first rotation, list the former key as `default`. Back up PostgreSQL before rotating.
A prior binary cannot read credentials created or rewrapped into the new envelope, so rollback
after rotation requires restoring that backup as well as the prior binary and configuration.

## Authenticate people

Local authentication is the default and registration is closed. Configure the bootstrap token,
then call `POST /operator/v1/organizations/{organization}/bootstrap` with that bearer token and
an email, display name, and password of at least 12 characters. This creates the deployment's
first Admin and cannot be repeated. Admins add local members with `POST .../members` and reset a
password with `PUT .../members/{user}/password`; a reset revokes existing sessions.

Passwords are versioned Argon2id verifiers. Sessions use Secure, HttpOnly, SameSite cookies, and
unsafe cookie-authenticated requests require an allowed `Origin`.

Set `authentication.mode` to `local+oidc` to add one generic OIDC provider. Register
`{server.public_url}/operator/v1/sign-in/callback` at the provider. An Admin pre-provisions each
person with `POST .../members/oidc`, supplying the exact OIDC `subject`, display name, and an
`admin`, `editor`, or `viewer` role. OpenCluster authenticates issuer and subject; the database
membership remains authoritative for authorization. Local Admin access remains for recovery.

### Upgrade from native SAML or SCIM

The last compatible build is `539b45e`. Before upgrading, use that build's
`GET .../members`, `GET .../identity-providers`, and `GET .../directory-groups` routes to save
every active user, Organization membership, role, and sign-in configuration as JSON. Retain a
database backup. Set `authentication.legacy_migration_complete` to `true` only after checking
that export, then upgrade, bootstrap the local Admin, and create equivalent local or
deployment-OIDC identities. Verify an Admin and one user of each role can sign in. Change the
provider callback only after validation.

The upgrade retains legacy identity-provider, SAML, SCIM, and directory-mapping rows. Startup
reads only whether an enabled provider or role-mapped directory group remains and refuses with
migration guidance unless the operator acknowledged the completed export. Runtime never
authenticates from or mutates those records. It never converts
or deletes them silently. Keep the backup and prior binary until checks pass. To roll back, stop
the new binary and restart the prior binary with its prior identity configuration.

## Environment compatibility reference

Existing deployments may continue to use environment variables during the compatibility
window. Variables that refer to credentials contain file paths, never secret values.

Legacy YAML remains accepted during this window. It must resolve every entry to the same
DSN file; multiple distinct databases refuse startup and must be consolidated first:

```yaml
database:
  placements:
    shared:
      dsn_file: "/run/secrets/postgres-dsn"
  assignments: {}
  default_placement: "shared"
```

Do not mix `database.dsn_file` with legacy database settings. A legacy operator or intake
address enables that route group on the shared HTTP listener and therefore must equal
`server.address`. Relay traffic remains on its separate gRPC listener.

### Migrate an existing deployment

Back up every configured database and keep a copy of the current binary and configuration.
Then inspect the DSN files named by the legacy settings:

- If every legacy entry reaches the same PostgreSQL database, replace the legacy database
  block with `database.dsn_file` pointing at that DSN file. Start one instance and require
  `/readyz` to return `200` before replacing the remaining instances.
- If the entries reach distinct databases, split them into one control-plane deployment per
  database. Give each deployment its former DSN file, the Organizations formerly assigned to
  that database, its existing sealing key, and unique HTTP and Relay addresses. Repoint every
  Alertmanager Integration webhook and Relay endpoint to the deployment that owns it. Register
  separate Slack, GitHub, and OIDC applications or callback URLs for each deployment when a
  provider cannot route callbacks by their authenticated Integration identity. Never select a
  deployment from an unauthenticated request body or opaque callback state. Validate webhooks,
  signed Slack events, OAuth and OIDC callbacks, and Relay connections before cutover, then verify
  incidents and Investigations before removing the old multi-database instance. If provider-side
  registrations cannot be split safely, remain on the prior binary until they can.

Do not combine data-only PostgreSQL dumps. User identities, installation keys, UUIDs, and
other deployment-wide unique values can collide even when Organization identifiers do not.
This release deliberately refuses an automatic merge instead of choosing which record wins.
Where one deployment is mandatory, remain on the prior binary until an application-aware
export/import workflow has resolved those collisions and validation shows every Organization's
record counts and Integrations in the destination.

Rollback is non-destructive: stop the new binary, restore the three legacy database settings
and the former listener addresses, then restart the prior binary. The consolidation release deletes no rows and
changes no table shape; the added database comment is safe for the prior binary to ignore. If
an operator-driven export/import changed data, restore the pre-migration backups instead.

Legacy inputs have no scheduled removal in the current release line. Removing one requires a
separately reviewed change that names the last compatible tag in this page at least one tagged
release before removal. Until that notice exists, the aliases and the rollback above remain
supported.

The shared HTTP server allows 10 seconds for headers, 30 seconds to read a request, 30 seconds
to write a response, and 60 seconds for an idle connection. Intake authentication, payload
size limits, and operator authorization remain enforced by their route owners inside those
connection bounds.

## Storage and process

| Variable | Required | Purpose |
| --- | --- | --- |
| `OC_HTTP_ADDRESS` | Yes | Shared health, metrics, operator, and intake listen address. |
| `OC_DATABASE_DSN_FILE` | Yes | File containing the deployment PostgreSQL DSN. |
| `OC_PLACEMENTS` | Legacy only | Comma-separated `name=dsn-file-path` entries. Every entry must name the same DSN file. |
| `OC_DEFAULT_PLACEMENT` | Legacy only | Accepted only with the legacy database settings. |
| `OC_PLACEMENT_ASSIGNMENTS` | Legacy only | Accepted only with the legacy database settings. |

| `OC_OTLP_ENDPOINT` | No | OTLP trace collector as `host:port`. Empty disables trace export. |

Do not set `OC_DATABASE_DSN_FILE` together with any legacy database variable. If the legacy
configuration names multiple distinct databases, consolidate them before upgrading.

## Integrations

| Variable | Required | Purpose |
| --- | --- | --- |
| `OC_SLACK_API_URL` | No | Slack API origin override. Empty uses Slack. |
| `OC_SLACK_CLIENT_ID` | For one-click install | The Slack app's OAuth client ID. Set with `OC_SLACK_CLIENT_SECRET_FILE` or neither. |
| `OC_SLACK_CLIENT_SECRET_FILE` | For one-click install | File containing the Slack app's OAuth client secret. Without both, Slack is connected with the pasted-token form. |
| `OC_SLACK_SIGNING_SECRET_FILE` | For the Slack agent | File containing the Slack app's signing secret, which inbound events are verified against. Without it, no events endpoint is served and the integration reports its inbound capabilities as unavailable. Independent of the client credential. |
| `OC_SLACK_AGENT_ORGANIZATIONS` | No | Comma-separated organizations the Slack agent surface is live for. Unset means none, which is the default. An inbound event for an organization outside it is acknowledged and dropped; reads through the Slack tools are unaffected either way. |
| `OC_GITHUB_APP_ID` | With GitHub | GitHub App ID. |
| `OC_GITHUB_APP_PRIVATE_KEY_FILE` | With GitHub | File containing the App private key in PEM format. |
| `OC_GITHUB_API_URL` | No | GitHub API origin. Use `https://HOST/api/v3` for GitHub Enterprise Server. |
| `OC_GITHUB_APP_SLUG` | For one-click install | The App's URL slug, from `https://github.com/apps/SLUG`. |
| `OC_GITHUB_APP_CLIENT_ID` | For one-click install | The App's OAuth client ID. |
| `OC_GITHUB_APP_CLIENT_SECRET_FILE` | For one-click install | File containing the App's OAuth client secret. |
| `OC_GITHUB_WEB_URL` | No | GitHub browser origin. Use `https://HOST` for GitHub Enterprise Server. |

The Slack app's request URL is `POST {intake origin}/intake/v1/slack/events`. It is served only
where `OC_SLACK_SIGNING_SECRET_FILE` is set — a deployment without one serves no events endpoint
at all rather than one that refuses everything.

`OC_SLACK_AGENT_ORGANIZATIONS` is a staged-rollout gate and not a customer setting: it exists so
the agent surface can be enabled for one workspace at a time, and it is removed when the surface
is generally available. It is not the only switch. An organization that has not connected Slack
does not have Slack, and disabling a Slack integration stops both reading and answering.

The GitHub App ID and key file are required together. The slug, client ID, and client
secret file are required together and enable **Connect GitHub**; without them, GitHub is
connected by entering an installation ID. Enabling the one-click flow also requires
`OC_OPERATOR_PUBLIC_URL`, because GitHub returns the browser to an absolute callback URL.

Slack requires `OC_SEALING_KEY_FILE` because its token is stored encrypted. GitHub stores
no credential at all.

## Conversations

Conversations let an operator ask follow-up questions in one context. They are off until
you turn them on; single-shot investigations are unaffected either way.

| Variable | Required | Purpose |
| --- | --- | --- |
| `OC_CONVERSATIONS_ENABLED` | No | `true` serves the conversation routes. Default: `false`, and every conversation route answers `404`. |
| `OC_ORG_MAX_CONCURRENT_INVESTIGATIONS` | No | Investigations one organization may run at once. Default: `4`. |
| `OC_ORG_MAX_WAITING_INVESTIGATIONS` | No | Investigations one organization may queue behind those. Opening past it is refused. Default: `16`. |
| `OC_MODEL_CONTEXT_WINDOW` | No | The model's context window in tokens. Default: resolved from the model name, or `128000` for a model this build does not recognise. |
| `OC_CONTEXT_THRESHOLD_PERCENT` | No | How full a conversation's estimated context may get before older turns are summarized. `1`–`99`. Default: `50`. |

The two per-organization ceilings are what keep one tenant from consuming the deployment.
Work above the concurrency ceiling waits rather than failing; work above the queue ceiling
is refused with a plain reason.

Raise `OC_MODEL_CONTEXT_WINDOW` only if you know your model's window is larger than the
default this build resolves. Setting it too high does not produce an error — it produces
turns that fail when the provider rejects an oversized request.

Provider consent is deployment-wide. Review [what is sent to the model
provider](/security/credentials-and-data-access#data-sent-to-the-model-provider) before
enabling investigations.

## Validation rules

- Public URLs and vendor overrides require HTTPS except on loopback.
- Partial GitHub or model-provider credentials refuse startup.
- Enabling the operator listener requires a sealing key because the catalog accepts
  Slack credentials.
- An unlisted model provider cannot receive investigation data.
- The first invalid setting stops startup and names the variable to fix.
