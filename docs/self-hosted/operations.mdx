Use the shared HTTP listener for probes, metrics, operator access, and intake. Apply
path-based proxy policy where these routes need different exposure. Keep Relay on its
separate network policy.

## Health and metrics

- `/healthz` reports process liveness without checking dependencies.
- `/readyz` reports whether this instance can reach its PostgreSQL database.
- `/metrics` exposes Prometheus metrics without organization labels.

Alert on sustained readiness failures, failed or degraded integration verification,
disconnected or outdated Relays, and failed investigations.

## What this deployment serves

`GET /operator/v1` answers a description of the running deployment. Any signed-in caller may
read it; it describes the deployment rather than a tenant, so it needs no permission and is not
public.

| It says | Which answers |
| --- | --- |
| Optional surfaces, each with whether this deployment serves it | "Are conversations on here?" without reading configuration or interpreting a `404` |
| Every route served, with the access and permission each requires | "Which sign-in routes exist?", "What does this role reach?" |
| Each listing's filters, sortable fields, default sort and searchability, and the shared paging rules | "How may I query this list?" |
| Each write's accepted body, as JSON Schema | "Why was my request refused?" — every write rejects a field it does not declare |

It is derived from the running route table and each capability's own declarations, so it cannot
describe a deployment other than the one answering. A console reads it instead of guessing; when
troubleshooting, it is the fastest way to confirm what a deployment is actually serving.

## Background work


| Work | Schedule or trigger |
| --- | --- |
| Audit retention | Hourly, using each organization's retention setting |
| Kubernetes change-history retention | Hourly, using `OC_CHANGE_LEDGER_RETENTION_DAYS` |
| Relay inventory synchronization | `OC_INVENTORY_INTERVAL` |
| Investigation execution | After an investigation opens, with bounded concurrency |

## Deploy and stop

Migrations are forward-only and run under a database lock at startup. Multiple new
instances can start without racing the schema. Review release notes and back up the
database before upgrading.

On `SIGTERM`, OpenCluster stops accepting new work and drains requests within
`OC_SHUTDOWN_TIMEOUT`. Investigations still running when shutdown completes are marked
failed rather than left running.

For a Phase 2 rollback, stop the new binary, restore the legacy database and listener inputs,
and restart the prior binary. No row or table shape is removed by this phase. Follow the
[single-database migration procedure](/self-hosted/configuration#migrate-an-existing-deployment)
before upgrading a deployment that currently reaches several databases.

## Integration health

Verification is a point-in-time check. Alertmanager verification reports the last
accepted delivery, so use its timestamp rather than status alone. Slack and GitHub
verification checks the vendor live. Kubernetes verification checks the current Relay
session and advertised capabilities.

## Retention

Audit entries use each organization's configured retention. Kubernetes change history
uses the deployment setting. Signals, incidents, investigations, and investigation
provenance remain operational records and can prevent integration deletion.
